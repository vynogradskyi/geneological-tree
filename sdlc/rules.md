# Постоянные правила проекта

Актуализировано: 27.11.2026. Эти правила сохраняют согласованные решения между рабочими сессиями. Более позднее явное указание пользователя имеет приоритет; после изменения решения обновить документацию.

## Назначение и текущий объём

- Проект — школьное «Moje drzewo genealogiczne». Базовые требования: минимум до прадедушек и прабабушек, максимально доступные поколения, формат итоговой работы не менее A3, эстетика и читаемость, название и автор, понимание ребёнком источников сведений. Фото — дополнительное требование пользователя.
- Ошибочно присланный материал «Okiem badacza» к проекту не относится.
- Сайт — публичный read-only просмотр: карточки, поиск, фото и PDF. 27.11.2026 пользователь решил убрать клиентский вход «Jestem z rodziny» вместе с браузерным редактором (черновики в браузере, ZIP-экспорт). Входа на сайте нет; будущий настоящий вход — только через платформу (см. `firebase-backend-plan.md`).
- Уже созданный локальный редактор разрешён для работы с основными данными. Его сервер рассчитан на localhost; не выставлять его в интернет как production backend.
- Ручное перетаскивание карточек удалено 27.11.2026 (не использовалось). Раскладку задаёт только алгоритм `web/family-layout.js` и подтверждённые предпочтения в `Data/Project/family-presentation.json`; перетаскивание по дереву двигает вид.
- 24.11.2026 пользователь запросил план следующей фазы: семейный вход с редактированием и загрузкой фото, затем JSON и языки PL/RU/EN. Пользователь разрешил реализацию по порядку, отдельным коммитом для каждой из трёх задач (вход, языки, оформление карточек); публикация выполняется отдельно; гостевой режим остаётся read-only. Порядок и нерешённые вопросы записаны в `sdlc.md`.
- Для первой задачи пользователь выбрал клиентский вход из публичного JSON как прототип. Допускается включать в исходники и публиковать предназначенные для прототипа логины, отображаемые имена и хеши паролей с солью; исходные пароли в Git не сохранять. Такой вход не защищает серверную запись. На этапе прототипа правки и загруженные фото сохраняются в браузере с ZIP-экспортом, без автоматического изменения общего сайта.
- По решению пользователя от 26.11.2026 контактные данные (Facebook, Instagram, телефон, WhatsApp, Telegram) доступны только семье с защищённым серверным доступом. Не включать контакты в публичные JSON, JS-снимки, офлайн-пакеты или Git; скрытие секции и клиентский вход не являются защитой. Реализация STORY-010 зависит от настоящей аутентификации, семейного членства и проверки прав, см. `firebase-backend-plan.md`; это требование не означает, что дерево уже интегрировано с общим backend или контакты перенесены.
- По запросу от 26.11.2026 создана STORY-011 на серверную часть, базу и перенос фото в облако. Это постановка будущего перехода, не изменение текущего режима прототипа. Миграция сохраняет ID, сведения, назначения фото, локальные оригиналы и разрешённый публичный просмотр; приватные материалы и контакты не становятся публичными. Параметры ресурсов, прав, расходов и выпуска определяются по `firebase-backend-plan.md`, текущий localhost-сервер не публикуется в интернет. Выполненную миграцию и фактическое изменение источников фиксировать отдельно в `sdlc.md` и `deploy.md`.

## Данные и подтверждение сведений

- Канонические сведения дерева — на польском; интерфейс и текстовые переводы доступны на PL/RU/EN. Русские и украинские сведения для канонической записи переводить; новые имена без заданной латиницы оформлять польской транскрипцией исходного текста. Уже утверждённое пользователем латинское написание сохранять точно, даже если оно отличается от стандартной транскрипции.
- Многоязычная версия поддерживает польский, русский и английский. Текущее польское написание сохранить; варианты имён на других языках не считать подтверждёнными без источника или согласования. Канонический польский формат и постоянные ID сохраняются; перевод не меняет даты и связи.
- Использовать постоянный уникальный `id` человека. `Mommy` и `Daddy` — ID соответствующих записей либо `null`. Сохранять регистр и имена полей текущей схемы.
- `photo` — относительный путь к назначенному файлу либо `null`. Неизвестные имена, даты, места и связи не придумывать. Не менять ID ради исправления написания имени.
- Для родственника собирать имя и фамилию, девичью фамилию женщины, годы/даты жизни, город или населённый пункт и страну рождения, братьев и сестёр с именами и годами рождения, фото и источник каждого уточнения. Предыдущие фамилии хранить отдельно от девичьей.
- Неоднозначные связи, имена, даты и принадлежность фото уточнять у пользователя. Обрыв установленной связи с основным человеком явно отмечать и заносить в локальный список вопросов. Не связывать людей только по совпавшей фамилии или внешности.
- Данные лежат в `Data/` (вне Git, кроме схемы): `Data/Information/family-tree.pl.json` — основной файл, `family-tree.ru.json` и `family-tree.en.json` — полные копии на других языках, `family-tree.schema.json` — схема; `Data/Photos` — фото; `Data/Project` — `family-tree-review.json` и `family-presentation.json`; `Data/Sources` — исходные материалы; `Data/Backups` — резервные копии редактора. Факты (ID, даты, связи, фото) меняются только в польском файле; RU/EN-копии отличаются лишь текстовыми полями.
- Сведения и спорные варианты хранить в `Data/Information` и `Data/Project/family-tree-review.json`, не только в сообщениях текущей сессии. Перед повторным вопросом искать уже сохранённый ответ.
- Неизвестная дата смерти показывается как `?`. `...` допустимо только при подтверждённом `isLiving: true`. Отсутствие даты смерти само по себе не подтверждает, что человек жив. Приблизительные сведения сохранять в предусмотренных полях/примечаниях.
- Проверять ссылки на родителей, братьев/сестёр и брачные отношения; не допускать циклов или противоречащих друг другу поколений. Не удалять неизвестное поле вместо корректного `null` в рамках текущей схемы.

## Фотографии

- Сохранять присланные индивидуальные фото без ретуши и генерации. Не заменять лицо или оригинал изображением, созданным ИИ.
- Для групповых фото использовать обычную программную обрезку без ИИ: подготовить отдельные портреты, показать пользователю и только после его одобрения назначать их людям как утверждённые фото. Технические черновики держать отдельно от назначенных материалов. Разрешение на программную обрезку уже получено; повторно спрашивать о самом методе не нужно.
- Сохранять исходный групповой снимок и источник. Удаление назначения фотографии не должно автоматически удалять исходный файл.
- Не определять личность по изображению самостоятельно: использовать подпись пользователя или запросить уточнение.

## Git и публикация

- По решениям 26–27.11.2026 общая личная платформа имеет отдельный репозиторий `vynogradskyi/platform` и Firebase backend `vynogradskyi-platform` на Blaze: Google Authentication, Firestore и будущий Storage. Публичный сайт дерева `familytree-9505c` остаётся Spark. Не переводить его на Blaze ради доступа к общей базе и не размещать приватные семейные материалы в его статических ресурсах.
- Общие ACL, поддерживаемые ID инструментов, Security Rules, серверные функции и управление пользователями реализуются и выпускаются из `platform`. В репозитории дерева реализуются его интерфейс, интеграционный адаптер, локальные проверки/источники и сборка публичного снимка. У каждого поддомена своя сессия Firebase Auth после Google-входа; передавать токены или общие session cookies между сайтами не требуется. Доступ проверяется к ресурсу инструмента, а не по имени поддомена.
- Источник прав платформы — `access/{uid}`: `enabled`, `globalRole` (`user/admin`), `email`, `apps` с ID `familyTree`/`todo` и ролями `viewer/editor`. Реальные назначения хранятся в Firestore и исключённых из Git локальных файлах, а не в статическом JSON сайта. Владелец уже получил `admin`; это не подключает дерево к облачной записи и не возобновляет отложенную STORY-011. Подробная карта состояния и будущих работ — в [firebase-backend-plan.md](firebase-backend-plan.md).

- GitHub содержит **только код, схему, синтетические примеры, тесты, конфигурацию и документацию**. Реальные семейные JSON, фотографии, исходные материалы, встроенные миниатюры, PDF, ZIP-пакеты и резервные копии не коммитить. Состав исключений — в `.gitignore`.
- Пользователь разрешил размещать реальные данные и фото на хостинге, а также публичный просмотр по адресу сайта. Это не отменяет запрет на добавление этих файлов в репозиторий.
- Ключи, токены и пароли не сохранять в исходники, Markdown, Git, вывод команд или сообщения. Использовать существующие авторизации, 1Password SSH-agent и GitHub Actions secret. Не экспортировать приватный SSH-ключ из 1Password.
- Git push по SSH и доступ GitHub API — разные механизмы. Для `gh` проверять аккаунт и права, не считать наличие SSH-ключа достаточным для управления секретами.
- Автодеплой кода должен сохранять текущие опубликованные фото/данные и прекращаться при ошибке проверки. Не подменять реальное дерево синтетическим примером при отсутствии локальных файлов или недоступности Hosting.
- Семейные обновления публикуются явно с локального компьютера через `scripts/publish_family.py`; обычный push кода их не отправляет. Подробности, учётные записи и откат — в [deploy.md](deploy.md).
- Не генерировать новый PDF/рендер при каждом обновлении сведений. Делать это по явному запросу пользователя; доступная посетителю кнопка PDF сохраняется.
