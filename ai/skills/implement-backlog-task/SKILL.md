# Реализация задачи из беклога

Чат реализации. Здесь работают только агенты `developer`, `qa-tester`, `devops` и одноразовый ревьюер без контекста. `product-manager` и `designer` в этом чате не запускаются: если нужно решение по требованиям или дизайну, остановись и задай вопрос владельцу.

Аргумент: ID задачи (`STORY-NNN` или `BUG-NNN`). Если ID не дан, покажи владельцу задачи из реестра со статусом «Готово к реализации» и спроси, какую брать.

Ты (главная сессия) — координатор: сам код не пишешь, а запускаешь агентов по шагам, передаёшь им результаты предыдущих шагов и ведёшь список задач (TaskCreate/TaskUpdate) по шагам ниже.

## Как запускать агентов
Роли описаны в `ai/agents/<имя>.md` (в Claude Code они же доступны через ссылку `.claude/agents/`). Запускай агента инструментом Agent с `subagent_type: <имя>` и передавай в промпте всё нужное: ID задачи, одобренный план, найденные проблемы — агент не видит этот чат.

Если такого типа агента нет в списке доступных или инструмент Agent недоступен (например, ты сам работаешь как субагент или это ChatGPT/Codex без субагентов), не останавливайся: прочитай файл роли и выполни шаг сам, строго в рамках этой роли, и помечай в отчёте, какая роль что сделала. Так процесс сохраняется даже без отдельных агентов.

Исключение — код-ревью (шаг 3): его ценность в том, что ревьюер не видел разработку. Если запустить свежего агента нельзя, проведи ревью отдельным проходом только по `git diff` и тексту задачи и честно напиши владельцу, что ревью было не независимым.

## Шаг 0. Проверка готовности (координатор)
1. Прочитай `AGENTS.md`, `sdlc/rules.md`, раздел задачи в `sdlc/backlog.md` и строку реестра.
2. Задача берётся только если:
   - статус «Готово к реализации» (или владелец прямо поручил её в этом чате);
   - есть критерии приёмки и раздел **Тест-кейсы**;
   - зависимости выполнены, задача не «Отложено пользователем» и не «Требует уточнения».
3. Если чего-то нет — остановись и напиши владельцу, чего не хватает (например: «нет тест-кейсов — их нужно добавить в чате беклога через /create-backlog-item»). Сам требования не дописывай.
4. Проверь `git status`: незакоммиченные изменения владельца не трогать; если они пересекаются с задачей — спроси владельца.
5. Прогони базовый набор тестов **до любых изменений** (команды в шаге 4) и запиши результат. Зачем: если что-то падает уже сейчас, это не вина новой реализации, и потом не придётся гадать. Падения или невозможность запуска (нет `.venv`, `locales/`, `scripts/`) сообщи владельцу вместе с планом и передай `developer` и `qa-tester`.

## Шаг 1. План — агент `developer`
Запусти `developer` с заданием: прочитать задачу, `sdlc/rules.md`, `sdlc/sdlc.md`, нужные разделы `sdlc/deploy.md` и `sdlc/design-rules.md` (для UI), изучить затронутый код и вернуть **план реализации** (без изменений файлов):
- что меняется и почему, по файлам;
- как будет выполнен каждый критерий приёмки;
- какие автотесты будут добавлены или изменены;
- риски и регрессии (раскладка, языки PL/RU/EN, режимы гость / семейный вход / локальный редактор, мобильные ширины);
- нужна ли работа `devops` (Firebase, CI, Hosting) и нужна ли публикация семейных данных;
- открытые вопросы.

Покажи план владельцу (SendUserMessage) и **дождись одобрения**. Если владелец заранее сказал «без подтверждения плана» — продолжай, но открытые вопросы всё равно задай. Переведи задачу в «В работе» в реестре и в карточке задачи.

## Шаг 2. Реализация — агент `developer`
Запусти `developer` с одобренным планом и комментариями владельца. Он реализует план, не коммитит и не пушит, прогоняет существующие тесты и возвращает список изменённых файлов и результат тестов.

Если задача требует инфраструктуры — параллельно или следом запусти `devops` с его частью плана (конфигурация Firebase, CI). Код приложения меняет только `developer`.

## Шаг 3. Код-ревью — новый агент без контекста
Запусти **свежего** агента `general-purpose` (не `fork` и не `developer` — у ревьюера не должно быть контекста разработки). Передай ему только:
- текст задачи из `sdlc/backlog.md` (цель, объём, критерии приёмки);
- указание прочитать `sdlc/rules.md`, `sdlc/design-rules.md` (для UI), `AGENTS.md`;
- команду посмотреть изменения: `git diff` и `git status` (для новых файлов).

Задание ревьюеру: найти ошибки корректности, нарушения правил проекта (семейные данные/фото/секреты в коде или Git, единый алгоритм раскладки без исключений для конкретных людей, гостевой режим только чтение, `?`/`...` для дат, переводы), регрессии, лишнюю сложность, несоответствие критериям. Вернуть список находок с файлом, строкой, серьёзностью (важно / мелочь) и сценарием отказа. Ревьюер ничего не правит.

Передай находки `developer`. Он исправляет важные, по мелочам решает сам и объясняет, что не стал менять и почему. Если исправления существенные — повтори шаг 3 с новым свежим ревьюером (не более двух повторов, затем спроси владельца).

## Шаг 4. Тесты — агент `developer`
`developer` покрывает задачу автотестами в `tests/` (Node `*.cjs` без npm, Python `*.py`), **только на синтетических данных** из `examples/`. Каждый автоматизируемый тест-кейс из задачи должен иметь тест. Затем полный прогон:
```sh
node tests/test_card_layout.cjs
python3 tests/test_hosted_build.py
.venv/bin/python tests/test_editor.py
git diff --check
```
Всё зелёное → `developer` заполняет в задаче «Результат реализации и проверки» (что сделано, какие тесты), задача переводится в «На проверке».

## Шаг 5. Проверка — агент `qa-tester`
Запусти `qa-tester` с задачей и списком изменений. Он:
- проходит **каждый тест-кейс из раздела «Тест-кейсы» задачи** и все критерии приёмки;
- проверяет соседние регрессии;
- для UI — ширины 320/390/430 CSS px, низкий альбомный режим, десктоп, языки PL/RU/EN, нужные режимы доступа;
- записывает в задачу результат по каждому тест-кейсу: пройден / не пройден / не проверен (с причиной и средой).

Есть провал → вернуть `developer` с шагами воспроизведения, фактическим и ожидаемым результатом; после исправления повторить шаги 4–5 (и шаг 3, если изменения существенные). Дефекты вне задачи не чинить — записать владельцу для чата беклога.

## Шаг 6. Коммит и выпуск — `developer`, затем `devops`
1. `developer` делает один связный коммит `feat|fix|docs: ... (STORY-NNN)`, перед этим сверяет `git status` с `.gitignore`: никаких реальных JSON, фото, `sources/`, `output/`, `backups/`, `tmp/`, PDF, ZIP, секретов.
2. **Push в `main` = production-деплой.** Перед push спроси владельца, если он не разрешил push заранее в этом чате.
3. После push запусти `devops`: проверить GitHub Actions и сайт (family-tree.vynogradskyi.com), не считать push успешным деплоем без проверки. Публикация семейных данных (`scripts/publish_family.py`) и PDF — только по явной просьбе владельца.
4. Записать в задачу «Публикация» (коммит, ссылка на Actions, что проверено), проверенные факты с датой — в `sdlc/sdlc.md`, процедурные изменения — в `sdlc/deploy.md`.
5. Статус: если все тест-кейсы пройдены и публикация проверена — «Закрыто» (с результатом и средой); иначе оставить «На проверке» и перечислить, что осталось.

## Итог владельцу
Коротко: что сделано, результат ревью и тестов, статус тест-кейсов, коммит и деплой, что не проверено, открытые вопросы для чата беклога.

## Всегда
- Не придумывать имена, даты, связи; неоднозначные семейные сведения — вопрос владельцу.
- Не делать reset --hard, force-push, переписывание истории без явного запроса.
- Не начинать отложенные задачи (STORY-011, зависимую STORY-010) без снятия паузы владельцем.
