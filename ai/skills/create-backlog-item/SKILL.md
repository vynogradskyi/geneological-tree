# Постановка задачи в беклог

Чат беклога. Здесь работают только `product-manager` и `qa-tester`. Код, семейные данные, фото, коммиты, push, деплой и PDF здесь не трогаются. Если нужны визуальные требования, которых нет в `sdlc/design-rules.md`, — записать открытый вопрос «нужно решение дизайнера» (это делается в отдельном чате с `designer`), а не придумывать дизайн.

Вход: описание от владельца (текст, скриншоты, ссылки на локальные материалы). Тип (STORY / BUG / EPIC) определяет `product-manager`; если неочевидно — спросить.

Ты (главная сессия) — координатор: запускаешь агентов по шагам и показываешь результат владельцу.

## Как запускать агентов
Роли описаны в `ai/agents/<имя>.md` (в Claude Code они же доступны через ссылку `.claude/agents/`). Запускай агента инструментом Agent с `subagent_type: <имя>` и передавай в промпте сообщение владельца и текущий текст задачи — агент не видит этот чат. Если такого типа агента нет или инструмент Agent недоступен (например, в ChatGPT/Codex), прочитай файл роли и выполни шаг сам в рамках этой роли, помечая, какая роль что сделала.

## Шаг 1. Формулировка — агент `product-manager`
Запусти `product-manager` с сообщением владельца и материалами. Он:
1. Читает `sdlc/rules.md`, `sdlc/sdlc.md`, начало `sdlc/backlog.md` (назначение, ведение задач, реестр), относящиеся разделы `sdlc/design-rules.md` / `sdlc/firebase-backend-plan.md`.
2. Ищет дубликаты и связанные задачи в реестре (и при необходимости смотрит код, чтобы понять, что уже работает).
   - Задача есть и ещё не закрыта — предлагает дополнить её, а не создавать новую.
   - Задача уже «Закрыто» или «Выполнено и опубликовано» — закрытую не переоткрывает (её результат и публикация уже зафиксированы), а предлагает новую задачу со ссылкой на неё в «Зависимостях» и описанием, чем новое пожелание отличается.
   - Если пожелание противоречит согласованному правилу (`sdlc/design-rules.md`, `sdlc/rules.md`) — прямо говорит об этом владельцу: изменение правила требует его решения.
3. Берёт следующий свободный ID (`STORY-NNN`, `BUG-NNN`, `EPIC-NNN`; ID не переиспользуются).
4. Пишет задачу по шаблону в конце `sdlc/backlog.md` («Шаблон стори» / «Шаблон бага»; эпик — цель, сценарий, границы, результат, открытые решения). Для бага отделяет сообщение пользователя, воспроизведённый дефект и гипотезу.
5. Ставит статус «Черновик», приоритет «Не определён» (своё предложение отмечает отдельно).
6. Реальные семейные подробности — обезличенно, с путём к локальному материалу. Присланные оригиналы (скриншоты, фото, схемы) и дословные подтверждения владельца сохраняются в `Data/Sources/<ГГГГ-ММ-ДД>_<ID>/`; производные файлы и отчёты туда не кладутся.
7. Неясности — в «Открытые вопросы», конкретно.

Покажи черновик владельцу и задай открытые вопросы. Ответы владельца передай `product-manager` для правки.

## Шаг 2. Тест-кейсы — агент `qa-tester` (только для STORY и BUG)
Запусти `qa-tester` с текстом задачи. Он:
1. Проверяет, что каждый критерий приёмки проверяем; непроверяемые возвращает `product-manager` с предложенной формулировкой.
2. Добавляет в задачу раздел **Тест-кейсы** сразу после «Критерии приёмки», в формате:
   ```markdown
   **Тест-кейсы:**
   | ID | Критерий | Предусловия / среда | Шаги | Ожидаемый результат | Авто/ручной |
   |---|---|---|---|---|---|
   | TC-STORY-NNN-01 | 1 | Гость, PL, 390 px | 1. … | … | Авто |
   ```
3. Покрывает: основной сценарий, граничные случаи, регрессии соседних правил (раскладка ветвей, `?`/`...`, языки PL/RU/EN/UK, режимы сайт / локальный редактор, ширины 320/390/430, низкий альбомный режим, десктоп — только относящиеся к задаче).
4. Отмечает, какие кейсы автоматизируются (синтетические данные, `tests/`) и какие проверяются вручную.
5. Держит объём соразмерным задаче: каждый критерий приёмки покрыт хотя бы одним кейсом, дополнительные — только для реальных рисков регрессии. Ориентир: небольшая задача или P3 — 3–7 кейсов, крупная — больше, но без повторов одного и того же сценария на разных ширинах, если их можно объединить в одном кейсе. Тест-кейсы читает исполнитель и тестировщик; лишние строки замедляют приёмку, не повышая качество.

Эпики тест-кейсов не получают — только при декомпозиции на стори.

## Шаг 3. Готовность — `product-manager`
1. Если открытых вопросов нет, критерии и тест-кейсы согласованы и владелец подтвердил — статус «Готово к реализации»; иначе «Черновик» или «Требует уточнения» с конкретным вопросом.
2. Обновить строку в реестре (`sdlc/backlog.md` → «Реестр»), зависимости и связи с другими задачами.
3. Новое общее правило в `sdlc/rules.md` / `sdlc/design-rules.md` — только после явного согласия владельца.

## Итог владельцу
ID и название, статус, кратко суть, число тест-кейсов (авто/ручные), оставшиеся вопросы. Напомнить, что реализация запускается в отдельном чате через `/implement-backlog-task <ID>`; статус «Готово к реализации» сам по себе не начинает работу.
