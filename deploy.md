# Деплой

Актуализировано: 24.11.2026. Текущая фаза — публичный сайт **только для чтения**.
В рабочей ветке подготовлен клиентский прототип семейного входа. Новые пакеты включают `web/family-auth.js`, `web/family-users.json`, браузерный редактор и ZIP-экспорт. Гость читает исходный снимок; после входа правки сохраняются в IndexedDB отдельно по логину. Серверной записи нет. Эта версия ещё не опубликована; описания прежнего production read-only ниже относятся к опубликованной базе.

Управление аккаунтами прототипа: `python3 scripts/manage_family_accounts.py --login LOGIN --first-name NAME --last-name SURNAME`; пароль вводится скрыто через getpass и сохраняется только как PBKDF2-хеш. `--generate` создаёт случайный пароль и записывает его в исключённый из Git файл `sources/family-prototype-credentials.txt`. Для существующего логина скрипт отказывается от неявной замены.

Краткий статус — в [sdlc.md](sdlc.md), постоянные ограничения — в [rules.md](rules.md).

## Автодеплой изменений кода

После push в `main` либо ручного запуска workflow через GitHub Actions:

1. Runner получает код репозитория и запускает проверки JavaScript, размещения карточек и сохранности размещённых данных.
2. `scripts/build_hosted.py` скачивает `hosting-data.json` с **фиксированного рабочего адреса** `https://familytree-9505c.web.app`.
3. Из Firebase скачиваются `web/family-data.js` и назначенные фотографии. SHA-256 каждого файла сверяется с манифестом; дополнительно проверяются допустимые пути, соответствие фотографий записям и соответствие карточек людям.
4. `scripts/readonly_assets.py` собирает актуальный код просмотрщика из репозитория. Скачанные данные и фото включаются без изменения содержимого.
5. Firebase action публикует `output/firebase/site` в канал `live`.

Таким образом, push кода сохраняет уже опубликованные семейные сведения. Локальные изменения записей сами в CI не передаются. Фото временно находятся на runner, но не включаются в Git, Actions artifacts или кэш сборки.

Сборка останавливается при отсутствующем снимке, ошибке скачивания, неверной контрольной сумме, несогласованном наборе фото или синтетическом примере. При неуспешной сборке шаг публикации не выполняется. Сохранность проверяется тестами в `tests/test_hosted_build.py`.

Workflow не запускает деплой для pull request. Он использует Node.js 22, Firebase CLI 15.37.0 и actions, закреплённые полными SHA. Публикации Actions выполняются последовательно: `concurrency.group: firebase-hosting-live`, `cancel-in-progress: false`. Таймаут задания — 15 минут.

Пользователь отдельно одобрил создание этого аккаунта, выдачу указанных ролей и передачу его JSON-ключа непосредственно в зашифрованный секрет данного репозитория. `firebase login` авторизует локальную публикацию. Этот вход не авторизует GitHub Actions. SSH-ключ GitHub, предоставляемый агентом 1Password, позволяет выполнять Git-операции, но не заменяет API-авторизацию `gh` для управления секретами и Actions. Для CLI `gh` нужен аккаунт с соответствующими правами на репозиторий.

Для замены CI-ключа обновить указанный GitHub secret и после проверки нового деплоя отозвать прежний ключ в Google Cloud IAM. Значения ключей не включать в документацию и логи.

## Первая публикация и изменения данных/фото

Выполнять на компьютере с основными семейными JSON и оригиналами фотографий. Чистого checkout из Git недостаточно: он содержит только синтетический пример.

Локальной сборке нужны Python 3.10+, Pillow, Node.js и Firebase CLI. При необходимости создать отдельное окружение:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
firebase login
```

Подготовить версию без отправки:

```sh
.venv/bin/python scripts/publish_family.py --build-only
```

Проверить подготовленные данные, фото и отсутствие редактора, затем при запросе на публикацию:

```sh
.venv/bin/python scripts/publish_family.py
```

Если выбранный `python3` уже содержит зависимости, команды можно запускать через него. На текущем компьютере launcher `Uruchom edytor.command` также умеет выбирать готовый Python из окружения Codex; переносимые инструкции не должны зависеть от этого локального пути.

`publish_family.py` создаёт свежий read-only пакет через `build_readonly.py`, копирует сайт в `output/firebase/site` и выполняет `firebase deploy --only hosting --project familytree-9505c`. `--build-only` выполняет только подготовку. Исходные семейные JSON и фото не изменяются.

Не выполнять ручную публикацию одновременно с GitHub Actions: локальный Firebase CLI не участвует в очереди Actions. Дождаться окончания текущего workflow и не запускать новый push до завершения ручной публикации.

Для отдельного переносимого пакета использовать `python3 scripts/build_readonly.py`: папка сайта и ZIP появятся в `output/hosting/familytree-…/`. Сам по себе этот шаг ничего не публикует. `build_html.py` обновляет локальный HTML-снимок, не публикует сайт и не генерирует PDF.

## Пользовательский домен

В Firebase Hosting добавлен `family-tree.vynogradskyi.com`. DNS-запись в GoDaddy:

| Type | Name | Value |
|---|---|---|
| CNAME | `family-tree` | `familytree-9505c.web.app` |

Это подтверждённые значения **этого проекта**, а не универсальный шаблон для другого сайта. При новых требованиях Firebase ориентироваться на записи его мастера подключения. Подтверждающие TXT-записи, если они требуются, сохранять согласно инструкции Firebase. Не менять записи корневого домена, почты или других поддоменов ради этого подключения.

Последняя проверка 24.11.2026: оба авторитетных DNS GoDaddy и публичные резолверы видят CNAME. Firebase сообщает `HOST_ACTIVE`, `OWNERSHIP_ACTIVE`, но сертификат ещё `CERT_VALIDATING`. Полная доступность по HTTPS пока не подтверждена. Ранее Safari показывал ошибку поиска сервера; прямое TLS-подключение обнаруживало сертификат без нового имени. Повторно проверить статус перед утверждением, что домен полностью подключён.

Для диагностики:

```sh
dig +short family-tree.vynogradskyi.com CNAME
dig @1.1.1.1 +short family-tree.vynogradskyi.com A
curl --head https://family-tree.vynogradskyi.com/
```

Выпуск сертификата может занять до 24 часов после настройки DNS. Не обходить проверку сертификата и не менять корректную запись только из-за ожидания. [Подключение домена в Firebase](https://firebase.google.com/docs/hosting/custom-domain).

Привязка домена не требует изменения приложения или workflow. Источник данных для CI остаётся на `web.app`, чтобы подключение пользовательского домена не влияло на сборку.

## Проверка результата и откат

- Проверить успешный запуск в [GitHub Actions](https://github.com/vynogradskyi/geneological-tree/actions), открыть сайт, карточку человека и фото; убедиться, что Edit и загрузка фото отсутствуют, PDF доступен.
- Проверить сохранность `hosting-data.json` и соответствие снимка данным до публикации. Не считать один успешный push доказательством успешного деплоя.
- Для отката Hosting выбрать предыдущий релиз в Firebase Console → Hosting. Откат возвращает и код, и снимок данных/фото этого релиза. Следующий автодеплой возьмёт данные из текущего, в том числе откаченного, live-релиза.
- Если live-данные потеряны, автоматический деплой из code-only репозитория их не восстановит. Восстановить локальные JSON/фото из резервной копии и выполнить явную публикацию через `publish_family.py`.
